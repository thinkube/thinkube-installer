= Add more nodes
:page-type: how-to

_Join another machine to a running cluster from thinkube-control, including one of a different CPU architecture, and build the images it needs._

.TL;DR
In thinkube-control open *Cluster Nodes*, press *Add Node*, enter the machine's address and wait: it is found, joined and configured. If the new machine is a different CPU architecture, run the image build from a terminal in Thinkube IDE as section 2 shows.

You add a node in two parts. The first runs in thinkube-control under *Cluster Nodes*: it finds the machine, joins it to the cluster, and configures it. The second runs in a terminal in Thinkube IDE when the new node brings a CPU architecture the cluster did not have: every container image must be built for it. Image builds take long and are worth retrying step by step, which is why they are a command rather than a button.

== Before you start

* The new machine meets the same requirements as the first ones — xref:node-setup.adoc[Prepare your machines]: Ubuntu Server 24.04, the same user and sudo password, OpenSSH server, internet access.
* The cluster is running and you can open thinkube-control.

thinkube-control installs Tailscale on the new node and joins it to your tailnet with the auth key the installer stored; nothing has to be run on the machine by hand.

== 1. Find and join the node

. In thinkube-control open *Cluster Nodes* and choose *Add Node*.
. Enter the network to scan, for example `192.168.1.0/24`. Several ranges may be given, separated by commas. Scan it.
. The wizard lists the machines it found with hostname, IP address, Ubuntu version and status. Select the ones to add. A machine that fails a requirement is marked, and the reason is shown.
. Continue to hardware detection. thinkube-control connects to each machine over SSH and reads its CPU architecture, its GPUs and its disks. If the architecture is new to the cluster, the wizard says so.
. Confirm the last step of the wizard.

The page streams what thinkube-control does, in this order:

. installs and configures Tailscale on the new node;
. joins the node to the Kubernetes cluster;
. cordons the node, so nothing is scheduled on it until setup finishes;
. disables the GPU operator on the node if it has no compatible GPU;
. configures SSH between the nodes;
. configures DNS on the new node;
. updates the code-server environment for the new node;
. hardens node logging against floods;
. applies the DGX Spark unified-memory tuning where the hardware is a Spark;
. deploys the GPU operator on the node and configures GPU time-slicing;
. prepares the JuiceFS directory the kubelet uses.

What happens next depends on the architecture.

*Same architecture as an existing node.* Every image already exists for it. thinkube-control restarts any pod that pulled a wrong-architecture image before the cordon took effect, uncordons the node, and reports it ready.

*New architecture.* The node stays cordoned. The page says which architectures now need images and shows the command to run.

== 2. Build the images for a new architecture

Open a terminal in Thinkube IDE and run the command the page showed:

[source,bash]
----
tk_images rebuild --uncordon <node1>,<node2>
----

`tk_images` runs three playbooks in sequence:

. *mirror* — mirrors the public images the platform uses from their registries into Thinkube Registry, one tag per architecture;
. *build-base* — builds the platform's base images natively on a node of each architecture; there is no emulation;
. *build-jupyter* — builds the notebook image with GPU support.

Each step checks Thinkube Registry for an existing per-architecture tag and skips what is already there, so a retry only builds what is missing. When all three succeed, `tk_images` records the architectures that have images and uncordons the nodes you named.

== If a step fails

The error is printed in the terminal. Fix its cause and run only the step that failed:

[source,bash]
----
tk_images mirror          # public images only
tk_images build-base      # base images only
tk_images build-jupyter   # the notebook image only
tk_images uncordon <node1>,<node2>
tk_images status          # which architectures have images, which nodes are cordoned
----

An image build that fails with `exec format error` pulled a base image that exists for one architecture only. Run `tk_images mirror` again, then retry the build.

== Remove a node

In thinkube-control, under *Cluster Nodes*, choose *Remove Node* on the node's row. thinkube-control drains its workloads, removes it from the cluster, and removes it from the inventory.

== Limits

* A new node must meet the same requirements as the first ones.
* The images for a new CPU architecture are built once, from Thinkube IDE, before that node can run them.
