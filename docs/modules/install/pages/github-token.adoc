= Connect to GitHub
:page-type: how-to

_Create the GitHub personal access token the installer asks for, and know exactly what the platform does with it._

.TL;DR
Create a GitHub personal access token with the scopes listed below and paste it into the installer. It logs `gh` in for you, lets you publish templates, reads your own template metadata, and keeps a backup of your certificate.

Your code and your deployments live in Thinkube Git, inside the cluster. GitHub is used for four things that sit outside it:

* Thinkube IDE logs the `gh` command-line tool in with the token, so `gh` works from a terminal without a browser.
* When you publish an application as a template, thinkube-control creates the repository under your GitHub account or organisation and pushes the code there.
* If you keep a metadata repository named `<your org>-metadata` with your own templates, the installer reads it and clones the templates marked for development into the IDE.
* The certificate playbook keeps an encrypted backup of your wildcard certificate in a private repository named `thinkube-certificates` under the same account.

Container images are stored in Thinkube Registry, not on GitHub.

== 1. Create the token

. Sign in to GitHub. Open your profile photo → *Settings* → *Developer settings* → *Personal access tokens* → *Tokens (classic)*.
. Choose *Generate new token (classic)*.
. Name it, for example `Thinkube`.
. Set an expiry. The token is used after the install too, so choose one you will remember to renew.
. Select these scopes. The installer checks for each of them and refuses a token that lacks one:
+
[cols="1,2",options="header"]
|===
| Scope | Why

| `repo` | Create and push the repositories above
| `workflow` | Push repositories that contain GitHub Actions workflows
| `write:packages` | Required by the check; `admin:packages` also satisfies it
| `read:org` | Read the organisation the repositories are created in
| `write:discussion` | Required by the check
|===
. *Generate token* and copy it now. Classic tokens start with `ghp_`.

== 2. Give it to the installer

The *Configuration* screen has two fields: *GitHub Personal Access Token* and *GitHub Organization or Username*. The installer calls GitHub with the token, reads the scopes GitHub reports for it, and shows a green mark when every required scope is present. A missing scope is named in the message.

== Where it goes

* `~/.env` on the machine running the installer, as `GITHUB_TOKEN` and `GITHUB_ORG`.
* `~/.env` on the control plane, copied by the `30_persist_user_secrets.yaml` playbook, so later operations do not need the laptop.
* thinkube-control receives it as a secret when it is deployed; that is what publishing a template uses.

== Rotating the token

Generate a new token with the same scopes. Replace the `GITHUB_TOKEN` line in `~/.env` on the control plane. thinkube-control reads the file when it is deployed, so run the `ansible/40_thinkube/core/thinkube-control/12_deploy.yaml` playbook of the `thinkube` repository again from Thinkube IDE. In the IDE, run `gh auth login --with-token` with the new token. Then revoke the old one on GitHub.

== Limits

* The token is stored in the cluster; rotating it means giving the new one to the platform as this page describes.
